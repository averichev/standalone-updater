# Как подключить обновления к Rust-приложению с SQLite и встроенным фронтендом

Выпускайте Rust-сервер и встроенные HTML, JS и CSS одним исполняемым файлом. Храните SQLite,
конфигурацию и пользовательские файлы по постоянным путям. После обновления сервер откроет ту же
базу и отдаст новый интерфейс. **При откате восстанавливается только бинарник.** Прежняя версия
должна уметь читать всё, что новая успела записать.

Ниже используется сервис `myapp` под Linux x86_64 или aarch64. Первый бинарник с поддержкой
обновлений доставьте обычным для проекта способом. Если проект также собирается для macOS и
Windows, ограничьте код установки атрибутом `#[cfg(target_os = "linux")]`. На остальных
поддерживаемых платформах доступны `UpdateMonitor` для проверки выпусков и `UpdateClient` для
проверки и загрузки.

## 1. Подключите библиотеку и выберите каталог

Для версии 0.1.0 нужен Rust 1.91 или новее. Добавьте зависимость в `Cargo.toml` приложения
и сохраните его `Cargo.lock`. Пока API экспериментален, закрепите проверенную ревизию Git.
При локальной разработке можно указать путь к соседней копии репозитория.
[Пример подключения по пути](../README.md#подключение-до-публикации)

```toml
[dependencies.standalone-updater]
git = "https://github.com/averichev/standalone-updater"
rev = "24e9e2b81987fca940ee013d591f16914f968b7a"
features = ["linux-runtime"]
```

Выберите режим по тому, кто владеет установленным файлом и процессом.

| Как развёрнут сервис | Режим | Что произойдёт |
| --- | --- | --- |
| Служба со стабильным PID, например под systemd | `Supervisor` | Исходный процесс запускает сервер из приватной рабочей копии. Исходный бинарник может принадлежать root. |
| Пользователь запускает принадлежащий ему бинарник, смена PID допустима | `Standalone` | Временный процесс заменяет установленный файл. Бинарник и его каталог принадлежат UID сервиса, каталог доступен для записи, а `staging` лежит на той же файловой системе. |
| Версии устанавливает пакетный менеджер или их доставляют с образом контейнера | `External` | Приложение проверяет выпуск. Установку и перезапуск выполняет существующая система доставки. |

Например, в режиме `Supervisor` можно использовать такую раскладку.

```text
/opt/myapp/myapp                  исходный бинарник со встроенным интерфейсом
/etc/myapp/update-source.json     доверенная конфигурация источника обновлений
/var/lib/myapp/app.sqlite3        рабочая база, рядом SQLite может создать -wal и -shm
/var/lib/myapp/updater/           рабочая копия бинарника, временные файлы и журнал
```

Задайте путь к БД в конфигурации приложения. Если искать БД рядом с исполняемым файлом,
сервер под `Supervisor` будет искать её в каталоге рабочей копии. Каталог `updater/` должен принадлежать UID сервиса,
иметь права `0700` и разрешать запуск файлов. Используйте реальные пути без симлинков и предков,
доступных посторонним для записи. Для контейнера сохраните БД и каталог обновлений между
запусками, если используете `Supervisor`.

Для внедрения и локальной проверки достаточно тестового источника. Стенд обновлятора
поднимает HTTP-сервер на loopback и подписывает тестовые выпуски одноразовым ключом.
[Проверка на двух сборках проекта](#проверка-на-двух-сборках-проекта)

При первом подключении подписанных обновлений сгенерируйте для своего приложения случайный UUID v4
и пару ключей Ed25519. В `update-source.json` сохраните UUID как `product_id`, а публичную часть
пары как JWK в поле `public_key`. Если приложение уже получает подписанные обновления, возьмите
его действующие значения. [Как создать UUID и ключ подписи](integration.md#как-создать-uuid-и-ключ-подписи)

Адрес проверки выпуска укажите в `descriptor_url`. Текущая версия
крейта также ожидает отдельный `manifest_url`, список разрешённых источников загрузки и лимит
размера бинарника. [Контракт источника](integration.md#источник-и-identity) ·
[Пример JSON для UpdateSource](../README.md#только-проверка)

## 2. Свяжите версию сборки с форматом данных

В `BuildInfo` нужны версия **приложения**, полный Rust target и отпечаток совместимости данных.
Передайте target из `build.rs` самого приложения. Для SQLx там же укажите каталог миграций,
чтобы Cargo заметил в том числе добавление файла.
[Документация sqlx::migrate!](https://docs.rs/sqlx/latest/sqlx/macro.migrate.html)

```rust
fn main() {
    let target = std::env::var("TARGET").expect("Cargo sets TARGET");
    println!("cargo:rustc-env=APP_BUILD_TARGET={target}");
    println!("cargo:rerun-if-changed=migrations");
}
```

Если проект использует SQLx, вычисляйте отпечаток из **того же набора встроенных миграций**,
который запускает сервер. Для примера добавьте `sha2 = "0.11"` в `[dependencies]` приложения и
включите возможности `migrate` и `macros` у SQLx. Функция использует версии и контрольные суммы
миграций прямого хода. Для её вызова не требуется подключение к SQLite.

```rust
use sha2::{Digest, Sha256};
use sqlx::migrate::Migrator;

static MIGRATOR: Migrator = sqlx::migrate!();

fn data_fingerprint() -> String {
    let mut hash = Sha256::new();
    let migrations = MIGRATOR.iter().filter(|m| m.migration_type.is_up_migration());
    for migration in migrations {
        hash.update(migration.version.to_be_bytes());
        hash.update(migration.checksum.as_ref());
    }
    hash.finalize()
        .iter()
        .map(|byte| format!("{byte:02x}"))
        .collect()
}
```

С `rusqlite` используйте тот же принцип для последовательности версий и контрольных сумм SQL,
которую применяет ваш мигратор. Если меняется формат записываемого JSON, сессий или файлов,
включите в отпечаток и версию соответствующего формата. Для приложения без постоянных данных
достаточно стабильной непустой метки. Версию релиза и содержимое фронтенда в отпечаток включать
не нужно.

## 3. Встройте обновлятор в запуск и остановку сервера

В начале асинхронного `main` на Linux ответьте на служебный запрос информации о сборке. Сделайте
это до чтения конфигурации, разбора обычных CLI-команд и инициализации логов. Затем подготовьте
конфигурацию для `runtime::launch`. В примере `PRODUCT_ID` — константа приложения с тем же UUID,
что в `UpdateSource`. Адрес и пути возьмите из тех же настроек, которыми пользуется сам сервис.

```rust
use standalone_updater::runtime::{
    self, BuildInfo, DataPolicy, InstallationMode, Launch, Readiness, RuntimeConfig,
    RECOVER_ARGUMENT, SERVER_ARGUMENT, WORKER_ARGUMENT,
};

let build = BuildInfo {
    version: env!("CARGO_PKG_VERSION").into(),
    rust_target: env!("APP_BUILD_TARGET").into(),
    product_id: PRODUCT_ID.into(),
    self_update_protocol: 1,
    data_compatibility: data_fingerprint(),
};
if build.handle_cli()? {
    return Ok(());
}

let mut arguments: Vec<_> = std::env::args().skip(1).collect();
if matches!(
    arguments.first().map(String::as_str),
    Some(SERVER_ARGUMENT | WORKER_ARGUMENT | RECOVER_ARGUMENT)
) {
    arguments.remove(0);
}
let config = RuntimeConfig {
    source: serde_json::from_slice(&std::fs::read("/etc/myapp/update-source.json")?)?,
    build,
    mode: InstallationMode::Supervisor,
    executable: std::env::current_exe()?,
    updates_directory: "/var/lib/myapp/updater".into(),
    arguments,
    working_directory: std::env::current_dir()?,
    data_policy: DataPolicy::RequireExact,
    readiness: Readiness::http("127.0.0.1:8080".parse()?, "/ready"),
};
let manager = match runtime::launch(config).await? {
    Launch::Exit(code) => std::process::exit(code),
    Launch::Serve(manager) => manager,
};
```

Только в ветке `Serve` открывайте пул, применяйте миграции (`MIGRATOR.run(&pool).await?` для
SQLx) и запускайте фоновые задачи и HTTP-сервер. Сохраните `UpdateManager` в состоянии
приложения. Если адрес или каталог задаются через CLI, разберите их из очищенных `arguments`
перед созданием `RuntimeConfig`. В режиме `Supervisor` пишите логи в stderr, поскольку stdout
сервера используется для управления обновлением.

**Готовность.** Зарегистрируйте `GET /ready` как отдельный маршрут, доступный по loopback без
авторизации и перенаправлений. После инициализации проверьте рабочую БД через тот же пул. В этом
обработчике Axum таблица `settings` должна существовать, но может быть пустой. Подставьте
обязательную таблицу вашего приложения.

```rust
match sqlx::query("SELECT 1 FROM settings LIMIT 1")
    .fetch_optional(&app.pool)
    .await
{
    Ok(_) => Json(app.manager.ready_response()).into_response(),
    Err(_) => StatusCode::SERVICE_UNAVAILABLE.into_response(),
}
```

Ответ `ready_response()` содержит версию и одноразовый идентификатор запущенного процесса. При
ошибке запуска или проверки готовности обновлятор пытается восстановить предыдущий бинарник и
проверить готовность прежней версии.

**Остановка.** Добавьте `manager.shutdown_requested()` к ожиданию штатных SIGTERM/Ctrl-C.
Прекратите принимать запросы и новые фоновые задания, дождитесь текущих запросов, задач записи и
транзакций. После этого закройте пул, подтвердите остановку и сразу вернитесь из `main`.

```rust
tokio::time::timeout(std::time::Duration::from_secs(15), pool.close()).await?;
manager.finish_shutdown()?;
Ok(())
```

При ошибке или тайм-ауте на любом шаге верните ошибку до вызова `finish_shutdown()`. Этот вызов
подтверждает обновлятору, что процесс освободил ресурсы. В примере Axum показано, как ограничить
ожидание активных HTTP-запросов после сигнала остановки.
[Полный пример запуска, маршрутов и остановки](../examples/axum-service.rs)

## 4. Подключите экран обновления

Поместите операции в действующую админку с её авторизацией, проверкой Origin и защитой от CSRF
при cookie-сессиях. Пример Axum использует локальный bearer API и отклоняет браузерные запросы с
Origin. Для браузера используйте существующую сессию администратора. Все параметры источника
остаются на сервере.

| Действие в интерфейсе | Маршрут из примера | Как обработать ответ |
| --- | --- | --- |
| Проверить выпуск | `POST /update/check` → `manager.check()` | Сохраните `operation_id`. Опрашивайте `GET /update`, который возвращает `manager.summary()`. |
| Подготовить выбранную версию | `POST /update/prepare` → `manager.prepare(InstallRequest)` | При `status.state = available` и `installation_supported = true` передайте `operation_id` проверки в поле `check_id`, а `status.available.version` в поле `version`. Дождитесь `prepared`. Сервер продолжает обслуживать запросы. |
| Установить | `POST /update/install` → `manager.install(&id).await` | После подтверждения отправьте `{"operation_id":"…"}`. HTTP 202 означает принятие запроса. При разрыве соединения возобновите опрос `GET /update`. |

Покажите итог для той же операции по `status.state` и `current_version`. При `completed`
предложите перезагрузить вкладку, чтобы она получила встроенный UI новой версии. При
`rolled_back` покажите версию, к которой вернулся сервис. При `failed` выведите `status.message`
и проверьте `status.recovery_required`. При HTTP 409 перечитайте состояние операции.

Для HTML задайте `Cache-Control: no-cache`, для JS/CSS с хешем содержимого в имени допустим
длительный кэш. Тогда после перезагрузки браузер запросит актуальную страницу со ссылками на её
ресурсы.
[Кэширование версионированных ресурсов](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)

## 5. Опубликуйте подписанный выпуск

1. Повысьте стабильную SemVer-версию приложения, например с `1.4.0` до `1.4.1`. Соберите
   фронтенд штатной командой проекта, затем выполните
   `cargo build --locked --release --target x86_64-unknown-linux-gnu --bin myapp`. Существующий
   механизм встраивания, например `include_bytes!` или `rust-embed`, должен получить свежие
   ресурсы. Запустите сервис из каталога без внешнего `dist/` и проверьте, что он отдаёт HTML,
   JS и CSS.
2. На совместимой Linux-машине запустите **готовый к публикации** файл с
   `--standalone-updater-build-info` без конфигурации и БД. Он должен вывести JSON и
   завершиться. Проверьте версию, UUID, target и отпечаток. В протоколе этот target называется
   `linux-x86_64`. Если выпускаете и GNU, и musl для одной архитектуры, задайте для них
   отдельные URL дескрипторов, чтобы каждый клиент получал свой ABI.
3. После всех операций с бинарником, включая `strip`, вычислите его размер и SHA-256. Подпишите
   закрытым Ed25519-ключом метаданные v1 с полями `schema_version: 1`, `application_id` (UUID
   продукта), `version`, `os`, `arch`, `size_bytes` и `sha256` в нижнем регистре. Формат подписи
   — JWS Compact с заголовком `alg=EdDSA`, `typ=releases-standalone+jws`.
4. Сначала выложите готовый ELF-файл по HTTPS на разрешённом origin, затем откройте дескриптор.
   На `GET /descriptor/linux-x86_64?current_version=1.4.0` сервер отвечает HTTP 200 с
   JSON-полями `version`, `url` и `signed_metadata`. При отсутствии более новой версии верните
   HTTP 204. Путь задаёт ваш `descriptor_url`, параметр `current_version` добавляет клиент.
   Манифест v2 может дополнять выпуск описанием.
   [Пример подписания и сервера дескрипторов в классе Source](../scripts/e2e.py)

## Если релиз меняет SQLite или формат записей

`DataPolicy::RequireExact` сравнивает отпечатки при подготовке, пока работает старая версия.
Даже добавление столбца через новую миграцию изменит отпечаток и потребует ручного перехода.
Одинаковая схема тоже требует внимания, например если новый код начинает писать значение,
которое старый код не умеет читать. Для установок, где такие переходы всегда проводит оператор,
`DataPolicy::ManualOnly` оставляет проверку выпусков и блокирует подготовку и установку.

На время ручного перехода остановите сервис и все процессы, которые пишут в БД. Из нового
приватного каталога сделайте резервную копию и проверьте её. Команда `.backup` читает
согласованный снимок средствами SQLite, включая подтверждённые записи из `-wal`. Режим `rw`
требует существующий файл, поэтому опечатка в пути к БД прервёт команду.
[Команды SQLite CLI](https://www.sqlite.org/cli.html) и
[устройство WAL](https://www.sqlite.org/wal.html)

```sh
sqlite3 'file:/var/lib/myapp/app.sqlite3?mode=rw' '.backup app-before-migration.sqlite3'
sqlite3 'file:app-before-migration.sqlite3?mode=rw' 'PRAGMA integrity_check;'
```

Ожидаемый результат проверки — `ok`. Сохраните бинарник фактически работающей версии и остальные
данные, формат которых меняется. В `Supervisor` версия рабочей копии может быть новее исходного
файла. Её путь возвращает `runtime::active_executable(&config)`.

Установите новую версию обычным способом (для `Supervisor` замените исходный бинарник),
примените миграции и проверьте контрольную запись до открытия доступа на запись. Если миграция
сорвалась, остановите процессы и восстановите совместимую пару из прежнего бинарника и
проверенного снимка БД. Восстанавливайте SQLite в чистый путь без оставшихся журналов другой
версии. При возврате к снимку будут потеряны записи, сделанные после него.

## Проверка на двух сборках проекта

На тестовой БД создайте запись через интерфейс версии `1.4.0`. Подготовьте подписанную `1.4.1` с
видимым изменением во фронтенде и теми же миграциями.

| Что испытать | Наблюдаемый результат |
| --- | --- |
| Дойти до `prepared`, отключить источник релизов и подтвердить установку | Состояние `completed`, `current_version = 1.4.1`. После перезагрузки вкладки видны новый UI и прежняя запись. Сервис перезапускается и с выключенным источником. |
| Дать следующей подписанной сборке вернуть 503 на `/ready` | После отката состояние `rolled_back`, прежние UI и API работают, запись читается. |
| Добавить миграцию в отдельную тестовую сборку | Подготовка завершается с `failed` до остановки сервера. Работающая версия по-прежнему читает и записывает в свою базу. |
| Прервать установку после начала замены | В `Supervisor` перезапустите исходный бинарник. В `Standalone` при `recovery_required` остановите все процессы приложения, выполните `myapp --standalone-updater-recover` с прежней конфигурацией и аргументами и запустите сервис как обычно. Проверьте рабочую версию и запись. |

Для отдельной проверки самого обновлятора выполните в его репозитории
`python3 scripts/e2e.py --native` на Linux или `python3 scripts/e2e.py` на macOS с Docker. Этот
стенд использует обычный файл данных. Проверку SQLite и браузера проводите на сборках своего
приложения. [Справочник по API, состояниям и восстановлению](integration.md)
